CopperNova (CNFS)

An experimental extent-based filesystem for Amiga hard disks.

Technical card

SpecificationValue

Volume label length30 Latin-1 characters

Sizes use multiples of 1,024 (1 kB = 1,024 bytes).

The partition maximum is 16 EB minus one allocation unit. The value above uses 512-byte units. With 4 kB units, the maximum is 16 EB − 4 kB. Each allocation unit must contain whole device sectors. Partitions extending beyond the 4 GB device boundary require TD64.

Build the handler

Install .NET 10 and place CopperSharp68k beside CopperFS. From the CopperFS root, build the standalone MC68000 handler with PowerShell.

./build/Build-Cpx4Handler.ps1

The output is artifacts/native-cpx4-handler/CopperCPX4. Use -CopperSharpRoot for a different toolchain checkout. The build writes a source manifest with the compiler and HUNK hashes. Handler build script.

Qualification evidence

14 November 2026. Coverage applies to the builds and workloads identified in the reports.

  • Host tests write and remount volumes with all ten supported sector and allocation-unit combinations. Fault injection covers interrupted writes, journal replay and damaged metadata. Host test methods · Geometry and remount results.
  • Compiled MC68000 tests mounted a 4 MB partition starting above the 4 GB device boundary using TD64. They also exercise geometry discovery and split requests. Device addressing tests.
  • Full-ROM emulation exercised wide DOS seek and read above the 4 GB position in a sparse file. The seven geometry-discovery workloads covered damaged-anchor fallback, formatting, file growth and journal recovery. Sparse-file workload · Geometry workloads.
  • Physical hardware. Maximum physical-drive capacity, controller compatibility and SSD discard remain unqualified. Open acceptance gates.

Machine and memory

The geometry-discovery build ran on an emulated MC68000 with Kickstart 3.1 and 512 kB of Chip RAM. Loaded segments used 176,264 bytes, the working arena used 68 kB, and OS and device allocations added 1,272 bytes at mount. Peak stack use across the seven workloads was 1,688 bytes out of 4 kB allocated. Memory measurements by workload.
